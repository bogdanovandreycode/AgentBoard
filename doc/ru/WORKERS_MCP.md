# Воркеры и подключение MCP

## Шаг 1. Создайте воркера

В AgentBoard откройте **Workers → Add worker**. Выберите профиль клиента: Codex, Claude Code, Gemini CLI, Cursor, OpenCode, Ollama via OpenCode, VS Code Copilot или другой MCP-клиент. Профиль заполняет типичные возможности (код, тесты, Git); вы можете их поменять. Имя видно на доске, а `Slug` — короткий идентификатор без пробелов для команды MCP. Нажмите **Save**.

Один воркер соответствует одной AI-личности. Для разных клиентов или команд создайте разных воркеров. Профиль возможностей описывает специализацию, но не расширяет права AI на этапы задач.

## Шаг 2. Скопируйте конфигурацию

Откройте созданного воркера. В блоке **MCP diagnostics** показан конфигурационный фрагмент и файл, куда его добавить. Нажмите **Copy MCP config**. Если файл уже существует, добавьте предложенный сервер в существующий объект `mcpServers`/`servers`/`mcp`, не стирая другие серверы.

Главная команда выглядит так:

```text
agentboard mcp --worker codex
```

`--worker` — `Slug` созданного воркера. MCP-клиент запускает эту команду сам, когда ему нужны инструменты.

### MCP работает без веб-интерфейса

`agentboard mcp` — отдельный stdio-процесс, который сам открывает базу AgentBoard. Ему не нужен `agentboard open`/`serve`, он не зависит от папки, из которой запущен веб-интерфейс, и от того, сколько экземпляров веб-интерфейса запущено. Несколько агентов могут работать одновременно, каждый в своём проекте: каждый клиент запускает собственный MCP-процесс, и все они безопасно используют одну базу SQLite.

### Как выбирается проект

MCP-сервер запускается в любой папке. При первом вызове инструмента он привязывается к проекту:

1. `--project PATH`, если указан (подходит любая папка внутри зарегистрированного проекта);
2. иначе рабочие папки клиента (roots), если клиент их сообщает;
3. иначе папка, в которой клиент запустил MCP-сервер.

`get_my_board` возвращает выбранный проект и воркера в `session` вместе с `binding_source`. Если рабочие папки клиента меняются, следующий вызов инструмента выполняет привязку заново. Без `--worker` используется единственный включённый воркер проекта.

Если привязка невозможна, каждый инструмент возвращает ошибку, которую агент должен передать пользователю; данные задач при этом не читаются:

| Код | Значение |
| --- | --- |
| `NO_PROJECTS` | В базе нет проектов. Выполните `agentboard init` в папке проекта и создайте воркера. Перезапуск не нужен. |
| `PROJECT_REQUIRED` | Рабочая папка вне зарегистрированных проектов. Сообщение перечисляет проекты. |
| `PROJECT_NOT_FOUND` | `--project` не находится внутри зарегистрированного проекта. |
| `PROJECT_AMBIGUOUS` | Рабочие папки клиента относятся к нескольким проектам. Добавьте `--project`. |
| `NO_WORKERS`, `WORKER_REQUIRED`, `WORKER_NOT_FOUND`, `WORKER_DISABLED` | Создайте, включите или выберите воркера через `--worker`. |

Конфигурации для **Codex** и **Gemini CLI** пользовательские и общие для всех папок, поэтому в них нет `--project`: создайте воркера с тем же slug в каждом проекте, где работает этот клиент. Файлы уровня проекта (Claude Code, Cursor, OpenCode, VS Code) содержат `--project` своего проекта.

### Явный проект и проверка контекста

Если указан `--project`, а папка запуска или рабочая папка клиента относится к другому проекту, инструменты запрашивают подтверждение через MCP elicitation. Клиенты без form elicitation получают `PROJECT_CONTEXT_MISMATCH` до доступа к задачам. Исправьте конфигурацию, уберите `--project` для автоопределения или явно подтвердите намеренную работу с другим проектом флагом `--allow-project-mismatch`. Смена рабочих папок сбрасывает прежние подтверждения. Автоматически определённые проекты подтверждения не требуют.

**Global settings → MCP project context** управляет этими проверками для всех проектов и воркеров одной базы. По умолчанию включено. Если выключить, MCP использует указанный проект без подтверждений и ошибок несовпадения. Уже открытые сессии применяют настройку при следующем вызове инструмента; видимость задач, переходы и правила человеческого тестирования продолжают соблюдаться.

В блоке диагностики после проверки указан абсолютный путь к запущенному `agentboard.exe`. Он особенно полезен при установке из ZIP. При установке через Scoop можно использовать команду `agentboard`, если клиент видит тот же `PATH`.

## Шаг 3. Добавьте сервер в свой клиент

В интерфейсе воркера уже есть готовый фрагмент. Ниже пояснение, где он используется:

| Клиент | Куда вставить | Как проверить на стороне клиента |
| --- | --- | --- |
| Codex | `%USERPROFILE%\.codex\config.toml`, секция `[mcp_servers.agentboard_<slug>]` | `codex mcp list` |
| Claude Code | `.mcp.json` в папке проекта | `claude mcp list` |
| Gemini CLI | `%USERPROFILE%\.gemini\settings.json`, объект `mcpServers` | `/mcp list` в Gemini CLI |
| Cursor | `.cursor\mcp.json` проекта | список MCP-серверов в настройках Cursor |
| OpenCode | `opencode.json` проекта, объект `mcp` | список MCP-инструментов в OpenCode |
| VS Code Copilot | `.vscode\mcp.json` проекта, объект `servers` | команда **MCP: List Servers** |

Примеры для Codex (пользовательская конфигурация, проект определяется автоматически) и Claude Code (файл проекта) с проектом `C:\Projects\MyFirstProject` и воркером `codex`:

```toml
# %USERPROFILE%\.codex\config.toml
[mcp_servers.agentboard_codex]
command = "agentboard"
args = ["mcp", "--worker", "codex"]
```

```json
{
  "mcpServers": {
    "agentboard_codex": {
      "type": "stdio",
      "command": "agentboard",
      "args": ["mcp", "--project", "C:\\Projects\\MyFirstProject", "--worker", "codex"]
    }
  }
}
```

В JSON обратная косая черта Windows удваивается; готовый фрагмент из интерфейса делает это автоматически. Сгенерированные конфигурации содержат фактический `--db` веб-сервера, поэтому HTTP и MCP используют одну базу, даже если окружение клиента отличается.

**Ollama** предоставляет локальную модель, но не заменяет MCP-клиент. Профиль **Ollama via OpenCode** генерирует MCP-настройку для OpenCode; отдельно настройте OpenCode на модель Ollama. Другой MCP-совместимый клиент с Ollama тоже подходит.

## Шаг 4. Проверьте подключение

1. Откройте карточку воркера и нажмите **Check again**. **Server check** запускает настоящий stdio-исполняемый файл с этим проектом, воркером и базой, проверяет рукопожатие, список инструментов и то, что проект и воркер находятся.
2. Запустите или перезапустите AI-клиент после добавления файла конфигурации. Попросите его вызвать `get_my_board`.
3. В AgentBoard появится **Client connected** и новая сессия в списке. Только это подтверждает подключение именно вашего клиента. Если есть инструменты, но клиент не подключён, проверьте путь к программе, имя файла конфигурации и его JSON/TOML-синтаксис.

Начинайте рабочую сессию с `get_my_board`. AI не получает задачи из `Backlog` и `Complete`, даже если знает их ID. AI не может притвориться человеком и не имеет общей команды «перенести куда угодно». Работа с файловой системой вне AgentBoard зависит от возможностей и песочницы выбранного клиента.

Каждый инструмент объявляет `title` и все четыре подсказки поведения MCP (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`) явными логическими значениями. Инструменты чтения только читают и идемпотентны; инструменты записи лишь добавляют записи или двигают задачи вперёд, поэтому ни один не является разрушающим и не выходит за пределы локальной базы AgentBoard.

Официальные инструкции клиентов: [Codex](https://developers.openai.com/learn/docs-mcp), [Claude Code](https://docs.anthropic.com/en/docs/claude-code/mcp), [Gemini CLI](https://geminicli.com/docs/tools/mcp-server/), [Cursor](https://prod.cursor.com/docs/cli/mcp), [OpenCode](https://opencode.ai/docs/mcp-servers/), [VS Code](https://code.visualstudio.com/docs/agent-customization/mcp-servers).
