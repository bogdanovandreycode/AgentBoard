# Воркери та підключення MCP

## Крок 1. Створіть воркера

В AgentBoard відкрийте **Workers → Add worker**. Виберіть профіль клієнта: Codex, Claude Code, Gemini CLI, Cursor, OpenCode, Ollama via OpenCode, VS Code Copilot або інший MCP-клієнт. Профіль заповнює типові можливості (код, тести, Git); Ви можете змінити їх. Ім'я видно на дошці, а `Slug` – короткий ідентифікатор без пропусків для команди MCP. Натисніть **Save**.

Один воркер відповідає одній AI-особі. Для різних клієнтів чи команд створіть різних воркерів. Профіль можливостей описує спеціалізацію, але з розширює права AI на етапи завдань.

## Крок 2. Скопіюйте конфігурацію

Відкрийте створений воркер. У блоці **MCP diagnostics** показано конфігураційний фрагмент та файл, куди його додати. Натисніть **Copy MCP config**. Якщо файл вже існує, додайте запропонований сервер до існуючого об'єкта `mcpServers`/`servers`/`mcp`, не стираючи інші сервери.

Головна команда виглядає так:

```text
agentboard mcp --worker codex
```

`--worker` - `Slug` створеного воркера. MCP-клієнт запускає цю команду сам, коли йому потрібні інструменти.

### MCP працює без веб-інтерфейсу

`agentboard mcp` - окремий stdio-процес, який сам відкриває базу AgentBoard. Йому не потрібний `agentboard open`/`serve`, він не залежить від папки, з якої запущено веб-інтерфейс, і від того, скільки екземплярів веб-інтерфейсу запущено. Декілька агентів можуть працювати одночасно, кожен у своєму проекті: кожен клієнт запускає власний MCP-процес, і всі вони безпечно використовують одну базу SQLite.

### Як вибирається проект

MCP-сервер запускається у будь-якій папці. При першому виклику інструмента він прив'язується до проекту:

1. `--project PATH`, якщо вказано (підходить будь-яка папка всередині зареєстрованого проекту);
2. інакше робочі папки клієнта (roots), якщо клієнт повідомляє;
3. інакше папка, у якій клієнт запустив MCP-сервер.

`get_my_board` повертає обраний проект та воркера в `session` разом із `binding_source`. Якщо робочі папки клієнта змінюються, наступний виклик інструмента знову прив'язується. Без `--worker` використовується єдиний увімкнений воркер проекту.

Якщо прив'язка неможлива, кожен інструмент повертає помилку, яку агент повинен передати користувачеві; дані завдань при цьому не читаються:

| Код | значення |
| --- | --- |
| `NO_PROJECTS` | В основі немає проектів. Виконайте `agentboard init` у папці проекту та створіть воркера. Перезапуск не потрібний. |
| `PROJECT_REQUIRED` | Робоча папка поза зареєстрованими проектами. Повідомлення перераховує проекти. |
| `PROJECT_NOT_FOUND` | `--project` не знаходиться всередині зареєстрованого проекту. |
| `PROJECT_AMBIGUOUS` | Робочі папки клієнта належать до кількох проектів. Додати `--project`. |
| `NO_WORKERS`, `WORKER_REQUIRED`, `WORKER_NOT_FOUND`, `WORKER_DISABLED` | Створіть, увімкніть або виберіть воркер через `--worker`. |

Конфігурації для **Codex** та **Gemini CLI** користувальницькі та спільні для всіх папок, тому в них немає `--project`: створіть воркера з тим самим slug у кожному проекті, де працює цей клієнт. Файли рівня проекту (Claude Code, Cursor, OpenCode, VS Code) містять свій проект `--project`.

### Явний проект та перевірка контексту

Якщо зазначено `--project`, а папка запуску або робоча папка клієнта відноситься до іншого проекту, інструменти запитують підтвердження через MCP elicitation. Клієнти без форми elicitation отримують `PROJECT_CONTEXT_MISMATCH` до доступу до завдань. Виправте конфігурацію, приберіть `--project` для автовизначення або явно підтвердіть навмисну ​​роботу з іншим проектом прапором `--allow-project-mismatch`. Зміна робочих папок скидає попередні підтвердження. Автоматично певні проекти підтвердження не вимагають.

**Global settings → MCP project context** керує цими перевірками для всіх проектів та воркерів однієї бази. За замовчуванням увімкнено. Якщо вимкнути, MCP використовує вказаний проект без підтверджень та помилок розбіжності. Вже відкриті сесії застосовують налаштування за наступного виклику інструмента; видимість завдань, переходи та правила людського тестування продовжують дотримуватися.

У блоці діагностики після перевірки вказано абсолютний шлях до запущеного `agentboard.exe`. Він особливо корисний при встановленні із ZIP. При установці через Scoop можна використовувати команду `agentboard`, якщо клієнт бачить той самий `PATH`.

## Крок 3. Додайте сервер до свого клієнта

В інтерфейсі воркера є готовий фрагмент. Нижче пояснення, де він використовується:

| Клієнт | куди вставити | Як перевірити на стороні клієнта
| --- | --- | --- |
| Codex | `%USERPROFILE%\.codex\config.toml`, секція `[mcp_servers.agentboard_<slug>]` | `codex mcp list` |
| Claude Code | `.mcp.json` у папці проекту | `claude mcp list` |
| Gemini CLI | `%USERPROFILE%\.gemini\settings.json`, об'єкт `mcpServers` | `/mcp list` у Gemini CLI |
| Cursor | Проекти `.cursor\mcp.json` | список MCP-серверів у налаштуваннях Cursor |
| OpenCode | `opencode.json` проекту, об'єкт `mcp` | список MCP-інструментів у OpenCode |
| VS Code Copilot | `.vscode\mcp.json` проекту, об'єкт `servers` | команда **MCP: List Servers** |

Приклади для Codex (конфігурація користувача, проект визначається автоматично) і Claude Code (файл проекту) з проектом `C:\Projects\MyFirstProject` і воркером `codex`:

```toml
# %USERPROFILE%\.codex\config.toml
[mcp_servers.agentboard_codex]
command = "agentboard"
args = ["mcp", "--worker", "codex"]
```

```json
{
  "mcpServers": {
    "agentboard_codex": {
      "type": "stdio",
      "command": "agentboard",
      "args": ["mcp", "--project", "C:\\Projects\\MyFirstProject", "--worker", "codex"]
    }
  }
}
```

У JSON зворотна коса характеристика Windows подвоюється; готовий фрагмент з інтерфейсу робить це автоматично. Згенеровані конфігурації містять фактичний `--db` веб-сервера, тому HTTP та MCP використовують одну базу, навіть якщо оточення клієнта відрізняється.

**Ollama** надає локальну модель, але не замінює MCP-клієнт. Профіль **Ollama via OpenCode** генерує MCP-налаштування для OpenCode; окремо налаштуйте OpenCode на Ollama. Інший MCP-сумісний клієнт із Ollama теж підходить.

## Крок 4. Перевірте підключення

1. Відкрийте картку воркера та натисніть **Check again**. **Server check** запускає справжній stdio-виконуваний файл з цим проектом, воркером та базою, перевіряє рукостискання, список інструментів та те, що проект та воркер знаходяться.
2. Запустіть або перезапустіть AI-клієнт після додавання конфігураційного файлу. Попросіть виклик виклику `get_my_board`.
3. В AgentBoard з'явиться **Client connected** та нова сесія у списку. Тільки це підтверджує підключення вашого клієнта. Якщо є інструменти, але клієнт не підключений, перевірте шлях до програми, ім'я конфігураційного файлу та його JSON/TOML-синтаксис.

Починайте робочу сесію із `get_my_board`. AI не отримує задач з `Backlog` і `Complete`, навіть якщо знає їх ID. AI не може прикинутися людиною і не має спільної команди "перенести куди завгодно". Робота з файловою системою поза AgentBoard залежить від можливостей та пісочниці обраного клієнта.

Кожен інструмент оголошує`title`і всі чотири підказки поведінки MCP (`readOnlyHint`,`destructiveHint`,`idempotentHint`,`openWorldHint`) явними логічними значеннями. Інструменти читання тільки читають та ідемпотентні; інструменти запису лише додають записи або рухають завдання вперед, тому жоден не є руйнівним і не виходить за межі локальної бази AgentBoard.

Офіційні інструкції клієнтів: [Codex](https://developers.openai.com/learn/docs-mcp), [Claude Code](https://docs.anthropic.com/en/docs/claude-code/mcp), [Gemini CLI](https://geminicli.com/docs/tools/mcp-server/), [Cursor](https://prod.cursor.com/docs/cli/mcp), [OpenCode](https://opencode.ai/docs/mcp-servers/), [VS Code](https://code.visualstudio.com/docs/agent-customization/mcp-servers).
